# Отчёт по проекту

Сервис собирает карточку товара для витрины «Полки» из названия, категории, характеристик и отзывов. Карточка валидна, когда витрина может подставить её в шаблон: один JSON-объект, пять полей, `product_id` того же товара, описание из 2–5 предложений и 120–700 символов, списки pros, cons и tags нужной длины. Смысл текста в метрику не входит.

Модель — Qwen2.5-1.5B-Instruct на vLLM. Внешнее сравнение — instruct-модель через OpenRouter, по умолчанию `openai/gpt-oss-20b`, ключ только из `OPENROUTER_API_KEY`.

## Финальный конфиг

- Модель `Qwen/Qwen2.5-1.5B-Instruct`, dtype `half` (float16), контекст 4096, `--gpu-memory-utilization 0.9`, `--enforce-eager`, порт 8000. Параметры генерации: temperature 0.3, top_p 0.9, top_k 20, repetition_penalty 1.1, max_tokens 350. JSON-режим: `guided`. `top_k` и `repetition_penalty` уходят в vLLM через `extra_body`.
- Стратегия длинного входа: снять шаблонные приставки отзывов («Коротко:», «Пользуюсь месяц.», «В целом» и соседние), схлопнуть одинаковые формулировки и оставить частоту. В бюджет 1500 токенов, посчитанный токенайзером модели вместе с шаблоном чата, на этих данных входят все уникальные мнения. Отдельный запрос на сжатие не используется.
- Повторов при браке формата: 2. До 2 запросов на карточку: первая попытка и ещё одна коррекция. В повтор уходит тот же диалог и список конкретных нарушений (нет поля, неверная длина, не то число предложений или пунктов). Дальше повторять невыгодно: каждая лишняя попытка на хвосте брака добавляет и время, и токены, а порог 80% уже должен держаться за счёт промпта и одной правки. Если проверка на всём dev оказывается ниже 80%, скрипт подбора сам поднимает лимит до 3 и только потом фиксирует конфиг.

Запуск сервера:

```bash
nohup vllm serve Qwen/Qwen2.5-1.5B-Instruct --dtype half --max-model-len 4096 \
  --gpu-memory-utilization 0.9 --enforce-eager --port 8000 > vllm.log 2>&1 &
```

Готовность: `curl -s http://localhost:8000/v1/models`.

## Сравнение с моделью через API

Локальный прогон — benchmark.jsonl, 300 товаров, concurrency 32. API — подвыборка dev.jsonl, 25 товаров, модель `openai/gpt-oss-20b`. Промпт один и тот же. В цену API подставлены токены из `usage` ответа OpenRouter и условный прайс 20 ₽ / 60 ₽ за миллион входных и выходных токенов. Токены локальной модели в эту формулу не подставляются: токенизация другая.

| | Локальная модель на vLLM | Модель через API |
| --- | --- | --- |
| Доля валидных карточек | 86.0% | 24.0% |
| Токенов на карточку, вход/выход | 1082 / 265 | 1773 / 623 |
| Время на карточку | 19.07 с | 7.55 с |
| Стоимость 1000 карточек | 11.30 ₽ | 72.83 ₽ |

Ошибки API и обработка:

В прогоне API ни один запрос не завершился ошибкой HTTP: счётчики 429, 400 и 5xx нулевые. Итоговый режим JSON на API — `object`. 429, 5xx и таймаут повторяются с паузой 1, 2, 4, … секунд, не больше пяти раз. 400 из-за параметра, которого нет у внешней модели, убирает top_k, repetition_penalty и seed и сразу повторяет запрос. Если схема guided_json не поддерживается, остаётся `json_object`, а если не поддерживается и он — обычный текст и разбор через json.loads. Слишком длинный для модели контекст ужимается и запрашивается снова. Карточка, которую так и не удалось получить, остаётся невалидной и не валит остальные.

В latency API входит сеть и очередь провайдера, у локальной модели этого слагаемого нет. Сравнивать скорость по этому столбцу как чистую скорость модели нельзя; для решения важны цена и доля валидных. Качество на задаче видно по доле валидных на одинаковом промпте. Что дешевле — по столбцу стоимости 1000 карточек и по расчёту в последнем разделе.

## Замеры

Скорость по concurrency:

Замер на 40 товарах benchmark.jsonl, те же параметры, что у финального прогона.

| concurrency | throughput, карт/с | latency, с | доля валидных | оценка времени на 300, с |
| --- | --- | --- | --- | --- |
| 1 | 0.226 | 4.42 | 90.0% | 1324.8 |
| 4 | 0.687 | 5.72 | 90.0% | 436.9 |
| 16 | 1.233 | 10.18 | 90.0% | 243.4 |
| 32 | 1.362 | 15.37 | 90.0% | 220.3 |

Рабочая точка — concurrency 32. Беру наибольший уровень, который прибавляет хотя бы 8% пропускной способности к уже выбранному и не роняет долю валидных больше чем на 8 пунктов относительно concurrency 1. Дальше плато: лишняя параллельность почти не ускоряет пакет и только растит очередь.

Итог полного прогона:

- доля валидных карточек: 258 из 300 (86.0%) на benchmark.jsonl, concurrency 32. Брак по причинам: предложений: 38, tags: 13, длина description: 12, pros: 7, cons: 7.
- скорость: рабочая точка concurrency 32, throughput 1.598 карт/с, средняя latency 19.07 с. Таблица throughput и latency по уровням concurrency приведена в этом разделе.
- время на весь бенчмарк: 187.735 с (3.1 мин) при n = 300.
- стоимость: на своём сервере 11.30 ₽/1000 из полного прогона (187.735 с, 300 карточек); через API 72.83 ₽/1000 из прогона этапа 6 (25 карточек, 44332 входных и 15568 выходных токенов).
- среднее число запросов на карточку, включая повтор при браке формата: 1.163. Длинный вход: максимум 1004 токенов на карточку, свыше 1500 — 0, с отброшенными отзывами — 0.

Пороги приёмки: доля валидных не ниже 80%, 300 карточек не дольше 8 минут, выбранный способ не дороже 25 ₽ за 1000.

## Длинный вход

У большинства товаров 4–25 отзывов. У популярных в benchmark их 90–220, суммарно до ~12 тысяч символов. Это больше 1500 токенов, если класть ленту как есть. Отзывы при этом сильно повторяются: одна и та же оценка приходит с приставками «Коротко:», «Что могу сказать:», «Пользуюсь месяц.», «Купил на замену старому.», «Брал для себя.», «В целом».

Стратегия — очистка и дедупликация, без второго запроса к модели.

1. Приставки снимаются, пробелы схлопываются, одинаковые формулировки считаются одним мнением. Рядом сохраняется частота, чтобы модель видела, что сказали 20 покупателей, а что трое.
2. Если промпт с частотами не влезает в 1500 токенов, частоты убираются.
3. Если не влезает и так, бинарным поиском оставляется смесь: около 70% слотов — самые частые мнения, остальные — самые редкие. Редкие нужны, потому что минусы в этих отзывах встречаются реже плюсов, и обрезка «только топ» оставила бы блок минусов без опоры.
4. Токены считаются `apply_chat_template` токенайзера Qwen, то есть так же, как их увидит сервер.

Отдельное сжатие отзывов моделью на длинных товарах удвоило бы число запросов примерно у 15% каталога и добавило бы и время, и выходные токены. После дедупликации терять уже почти нечего: остаются сами оценки, а не их копии.

В полном прогоне самый длинный вход — 1004 токенов, карточек длиннее 1500 — 0, с отброшенными отзывами — 0. Длинных товаров 45: в среднем 14.0 уникальных формулировок, в промпт вошло 14.0.

## Оптимизации

Точность — float16, флаг `--dtype half` из условия запуска.

Qwen2.5-1.5B в float16 занимает около 3 ГБ весов. На T4 с 16 ГБ это не упирается в память даже при контексте 4096 и запасе под батч, поэтому INT4 не покупает место под более крупную модель. Узкое место приёмки — доля валидного JSON, а не пропускная способность: порог 8 минут на 300 карточек для модели такого размера достижим и в float16. Квантизация в INT4 может ускорить чтение весов, но на 1.5B чаще растит долю обрывов и кривых списков. Каждый такой брак — это повторный запрос, и он съедает выигрыш по скорости. Пока полный прогон укладывается в 8 минут и в 25 ₽ за 1000, оставляю float16. Отдельный прогон INT4 имеет смысл только если float16 упрётся в один из этих двух порогов.

## Стоимость и решение

Обе цены — из формул условия.

Свой сервер, время и число карточек полного прогона benchmark.jsonl:

`(время_прогона_сек / 3600 × 65) / число_карточек × 1000`

API, токены и число карточек прогона этапа 6:

`(входные_токены × 20 + выходные_токены × 60) / 1 000 000 / число_карточек × 1000`

Плановый объём — 50 000 карточек в месяц. Порог приёмки — не дороже 25 ₽ за 1000 на выбранном способе. Аренда T4 считается и за простой: если ВМ поднимать под каждый короткий запуск, холодный старт оплачивается, даже когда карточек мало.



Полный прогон: 300 карточек за 187.7 с, это 11.30 ₽ за 1000 на своём сервере.

API `openai/gpt-oss-20b` на 25 карточках потратил 44332 входных и 15568 выходных токенов, это 72.83 ₽ за 1000.

На 50 000 карточек, если платить только за время генерации: свой сервер 565 ₽/мес, API 3641 ₽/мес.

Если ВМ поднимают под один прогон и закладывают 3 минуты холодного старта, API дешевле только пока в месяц меньше 53 карточек. Выше этой отметки разница в цене карточки перекрывает разовый старт.

Если ту же T4 держать включённой весь месяц, аренда стоит 46800 ₽ независимо от числа карточек. API остаётся дешевле, пока объём ниже 642603 карточек в месяц. 50 000 до этой границы не дотягивает, поэтому постоянно включённый GPU на плановом объёме дороже API.

При измеренной скорости 1.598 карт/с один месячный пакет на 50 000 карточек занимает 8.7 ч чистой генерации плюс старт: 568 ₽ при посекундной оплате и 585 ₽, если незавершённый час округляется вверх. Тридцать ежедневных включений с округлением до часа стоят 1950 ₽, потому что почти каждый день оплачивается полный час простоя после короткого пакета.

Итог для 50 000 карточек в месяц: свой сервер. 11.30 ₽ за 1000 ниже и порога 25 ₽, и цены API 72.83 ₽. ВМ включают на пакет и выключают. Постоянно держать T4 не нужно: на этом объёме простоя больше, чем работы. API оставляем для объёма, при котором отдельный запуск GPU не окупает даже холодный старт.

## Как воспроизвести

```bash
# сервер, в отдельном терминале
nohup vllm serve Qwen/Qwen2.5-1.5B-Instruct --dtype half --max-model-len 4096 \
  --gpu-memory-utilization 0.9 --enforce-eager --port 8000 > vllm.log 2>&1 &

# данные, сетка, бенчмарк, API, отчёт
export OPENROUTER_API_KEY=ваш_ключ   # только в окружении, не в коде
bash run_on_vm.sh
```

По отдельности: `python tune_params.py`, `python run_batch.py --sweep 1,4,16,32 --sweep-n 40`, `python run_batch.py`, `python compare_api.py`, `python check_metrics.py --write-readme`.

Проверка формул и валидатора без GPU: `python check_metrics.py --self-check` и `python -m unittest tests.test_core`.

Артефакты лежат в `outputs/`: `predictions.jsonl` — карточка на строку, `report.json` — факты прогона, метрики и сравнение с API. Метрики в `report.json` пересчитываются из времени, токенов и повторной валидации карточек, а не записываются вручную.
